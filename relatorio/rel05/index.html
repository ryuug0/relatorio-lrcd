1 Introdução

Este relatório aborda o desenvolvimento de um pacote de funções personalizado para o ambiente R, criado para resolver problemas práticos do meu dia a dia. O pacote, batizado de graf, conta com três funções principais: git(), mpot() e mdes(), que detalharei a seguir.

Um detalhe curioso: apesar do nome “graf”, o pacote não faz análises gráficas. Isso é apenas um resquício da proposta inicial do projeto, que acabei descartando porque já existem pacotes muito mais robustos e consolidados para gráficos, como o leem, o ggplot2 e as próprias funções nativas do R. O foco aqui virou produtividade e engenharia.

2 Instalação e Documentação do Pacote

Antes de usar qualquer uma dessas funções, o pacote precisava ser estruturado, documentado e instalado localmente no R. Para não ter que fazer nada disso na mão, utilizei a dupla de ouro da criação de pacotes: roxygen2 e devtools.

A organização e a documentação foram feitas direto no código, usando comentários especiais com #' e tags como @param e @export. Assim que o código fica pronto, utilizamos dois comandos essenciais no console para fazer a coisa toda funcionar:

  1. devtools::document(): Esse comando é fundamental. Ele varre o nosso script, lê todas aquelas marcações do roxygen, gera automaticamente as páginas de ajuda (o help do R) e, o mais importante, escreve o arquivo NAMESPACE. Isso garante que as nossas funções sejam exportadas corretamente sem dar conflito com o resto do R.
  2. devtools::install(): Depois que a documentação está gerada, esse comando pega a pasta do nosso projeto, compila tudo e instala de fato o pacote na biblioteca do R do nosso computador.

Só depois de rodar essa dupla é que podemos usar o famoso library(graf) para carregar o pacote e colocar as funções para trabalhar.

3 As Funções

3.1 git()

Essa função nasceu puramente do ódio de tentar publicar os relatórios da disciplina na página do GitHub Pages e ver que as coisas não atualizavam. Como a nossa estrutura de pastas tem vários diretórios filhos e aninhados (cheios de index.qmd e index.Rmd), rodar a renderização padrão causava vários bugs e deixava arquivos para trás.

A solução para automatizar essa dor de cabeça foi criar uma função que, partindo da raiz do projeto, faz uma busca recursiva em todas as pastas. Ela encontra os arquivos e roda o quarto render para os .qmd e o rmarkdown::render (knit) para os .Rmd. Isso garante que o projeto inteiro seja compilado, e não só o arquivo que está aberto no momento.

De quebra, para economizar tempo em testes, a função já emenda os comandos do terminal (git add ., git commit e git push), permitindo até enviar commits sem comentários (--allow-empty-message), o que agiliza muito a vida.

Abaixo, a lógica da função separada por etapas:

Renderizando todos os .qmd do projeto:

meu_git <- function(msg) {

  arquivos_qmd <- list.files(pattern = "\\.qmd$", recursive = TRUE, full.names = TRUE)
  if (length(arquivos_qmd) > 0) {
    message("=> Passo 1: Renderizando todos os arquivos .qmd...")
    for (qmd in arquivos_qmd) {
      message(paste("-> Renderizando:", basename(qmd)))
      system(paste("quarto render", shQuote(qmd)))
    }
  }

“Costurando” todos os .Rmd do projeto:

  arquivos_rmd <- list.files(pattern = "\\.[Rr]md$", recursive = TRUE, full.names = TRUE)
  if (length(arquivos_rmd) > 0) {
    message("=> Passo 2: Knitando todos os arquivos .Rmd...")
    for (rmd in arquivos_rmd) {
      message(paste("-> Knitando:", basename(rmd)))
      rmarkdown::render(rmd, quiet = TRUE)
    }
  }

Subindo tudo para o GitHub:

  message("=> Passo 3: Enviando tudo para o GitHub...")
  system("git add .")

  comando_commit <- sprintf('git commit --allow-empty-message -m "%s"', msg)
  system(comando_commit)

  system("git push")
  message("=> Feito! Tudo atualizado e no ar.")
}

3.2 mpot()

A próxima função ataca um problema diário que enfrento no meu estágio na oficina. Trabalho com manutenção e identificação de motores elétricos, e direto os equipamentos chegam com a placa de identificação ilegível ou danificada. Como os parâmetros do motor são amarrados uns aos outros, podemos descobrir a potência a partir da tensão, corrente, fator de potência, rendimento e número de fases.

É uma conta que daria para fazer na calculadora, claro, mas a ideia futura é escalar o pacote: inserir os dados que a gente tem e fazer o R buscar em catálogos qual é exatamente aquele motor. Por enquanto, como cruzar dados de catálogo dá bastante trabalho de gerenciamento de banco de dados, a função se limita a entregar o cálculo limpo da potência.

A potência elétrica ativa consumida da rede é dada, em kW, pela fórmula:

\[P_{kW} = \sqrt{3} \cdot V \cdot I \cdot F_P \cdot \eta\]

E para converter isso em Cavalos-Vapor (CV):

\[P_{cv} = P_{kW} \cdot 1,36\]

A função que montei é esperta o suficiente para olhar o número de fases (usando o \(\sqrt{3}\) apenas se for trifásico) e verificar se o usuário inseriu o rendimento \(\eta\). Se o rendimento não for informado, ela retorna a potência elétrica da rede; se for, ela entrega a potência mecânica real lá na ponta do eixo.

meu_mpot <- function(f, v, i, fp, rendimento) {
  fator <- ifelse(f == 3, sqrt(3), 1)
  p_kw <- (fator * v * i * fp) / 1000

  if (is.null(rendimento)) {
    tipo <- "Potência Elétrica Ativa"
  } else {
    tipo <- "Potência Mecânica no Eixo"
    p_kw <- p_kw * rendimento
  }

  p_cv <- p_kw * 1.35962

  list(
    Tipo = tipo,
    kW = round(p_kw, 2),
    CV = round(p_cv, 2)
  )
}

Aqui vai um exemplo rodando nativamente para um motor trifásico, com tensão de 380 V, corrente de 21,5 A, fator de potência de 0,92 e rendimento de 97%:

library(graf)

mpot(f = 3, v = 380, i = 21.5, fp = 0.92, rendimento = 0.97)
$Tipo
[1] "Potência Mecânica no Eixo"

$kW
[1] 12.63

$CV
[1] 17.17

3.3 mdes()

Essa última função também é voltada para a rotina com motores, mas o foco dela é a análise de falhas. A partir das correntes medidas nas fases do motor em funcionamento, ela calcula o desbalanceamento. Se a assimetria passar de 5%, a integridade do isolamento térmico do motor já corre sérios riscos.

A norma clássica (NEMA) manda calcular esse desbalanceamento usando a média das correntes. Só que, na oficina, a gente não gosta de média porque ela suaviza os problemas. Nós usamos a relação direta entre a maior corrente e a menor corrente medida. É um método muito mais conservador, rígido e que garante uma margem de segurança maior para o motor do cliente.

A fórmula pessimista que utilizamos é:

\[D_{\%} = \left(\frac{I_{max}}{I_{min}}-1\right)\cdot 100\]

A implementação tem um gatilho de segurança que joga um alerta vermelho no console do R se o resultado estourar o limite de 5%:

meu_mdes <- function(correntes) {
  n <- length(correntes)

  if (n == 1) {
    warning("Motores monofásicos não possuem desbalanceamento de fase.")
    return(NA)
  } else if (n >= 2) {
    desbal <- (((max(correntes) / min(correntes)) - 1) * 100)
  }

  if (!is.na(desbal) && desbal > 5) {
    warning("ALERTA: Desbalanceamento acima de 5% (risco de superaquecimento).")
  }

  return(round(desbal, 2))
}

Exemplo prático de uma medição onde o motor apresentou um leve desequilíbrio crítico nas fases (13.0 A, 14.5 A e 17.2 A):

correntes_medidas <- c(13.0, 14.5, 17.2)
mdes(correntes_medidas)
[1] 32.31
